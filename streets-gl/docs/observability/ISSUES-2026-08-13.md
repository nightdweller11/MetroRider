## V1 — building textures are wrong

> "something weird seems to have happened to textures around the station and in
> the world in general … something that happened in one of the versions lately
> has made the textures not actually apply correctly to the buildings."

Recent candidates, newest first: lineside sign meshes (v1.1.14), rigged
character loading (v1.1.10) which decodes GLB images to a 2D canvas, crowd
meshes rebuilt 5×/s (v1.1.9/v1.1.10), station geometry re-origin (v1.1.9),
motion-vector + TAA changes (v1.1.5).

**Hypothesis (ranked):**
1. Texture-atlas or tile eviction under memory pressure — see V3. If GPU memory
   climbs, the tile system drops and re-uploads building textures, which would
   look exactly like "changes texture every time" (V2).
2. `CharacterLoader` calls `createImageBitmap` + a 2D canvas at load. If that
   disturbs the WebGL context's active texture unit or pixel-store state, the
   next uploads land wrong.

## V2 — buildings pop in/out and re-texture on camera movement

> "moving the camera around at the station seems to be causing the buildings to
> come in and out of view, and they seem to change textures every time."
> "sometimes the correct texture is loaded and applied and then it switches to
> the strange texture that seems diagonally applied"

### MEASURED, 2026-08-13 — the operator's reading was right

Orbiting the camera at a station with the train STOPPED, for ten seconds:

| Signal | Value | Reading |
|---|---|---|
| Buffer creation, blamed | `createAttributeBuffer ← <tile mesh>.updateMesh` ×4 distinct classes | **tile meshes are being rebuilt by camera movement alone** |
| New VAOs | `bindVAO ← draw` for those same classes | each rebuild also makes a new VAO |
| Live buffers | **+1,000 / min** | churn is not being reclaimed fast enough |
| Live VAOs | **+619 / min** | same |
| Heap | **+1,975 MB / min** | this is the "load climbs" symptom, and it needs no driving at all |
| Texture uploads | 54–58 / sec, ALL from `updateWaterTileMask` / `updateTerrainTileMask` | terrain masks, not building textures |

Two conclusions that change the diagnosis:

1. **Building textures are NOT being re-uploaded.** Every texture upload during
   camera movement is a terrain/water mask. So "the texture changes" is not the
   image being replaced — it is the building MESH being rebuilt, and coming
   back with different per-vertex texture ids or a different LOD. The tile
   system is discarding and recreating work purely because the camera moved,
   exactly as the operator suspected.
2. **`UNPACK_FLIP_Y_WEBGL` is toggled 292–384 times** during a single orbit.
   Flip-Y is global WebGL state. A texture uploaded with the flag in the wrong
   position is applied upside down, and combined with a mismatched UV set that
   is precisely the "strange, diagonally applied" look. This is a strong second
   suspect and it is cheap to test: pin the flag and see whether the artifact
   survives.

### Next steps, in order

1. Count tile create/destroy events per second during a camera orbit (needs a
   handle on the tile system in `lib-drive.mjs`; `v.tiles instanceof Map` did
   not match the real field). If tiles are being evicted on camera movement,
   the eviction policy is the bug — a camera orbit does not change which tiles
   are near the train.
2. Pin `UNPACK_FLIP_Y_WEBGL` around every upload and re-run the visual-stability
   probe on the building regions; compare `flipPct` before and after.
3. Only then look at the mesh-rebuild path itself.

**Do not "fix" this by guessing.** The first hypothesis in this file (memory
pressure evicting building textures) is now DISPROVED by measurement — no
building texture was re-uploaded at all.

## V3 — load climbs over time

> "gpu usage, and load on the machine — it seems to have gone way up and seems
> to be going higher the longer i am in the game — this wasn't the case before."

**Primary hypothesis: a GPU resource leak from meshes I rebuild every frame or
every few frames.** v1.1.9 onward rebuilds crowd meshes ~5×/s and sign meshes
every 0.5 s, each time constructing a new `TrainMeshObject`. If removing an
object from the scene does not delete its GPU buffers, the leak is continuous
and grows exactly with time played — and it would explain V1/V2 as a
consequence (memory pressure → texture eviction).

**This must be measured, not argued.** The tool is a live count of WebGL
objects (buffers, textures, VAOs) sampled over minutes of driving.

## V4 — passengers all look the same

> "they have no variability, they need to have different clothes and skin, and
> have some different models there as well."

The rigged character bakes ONE set of vertex colours from its texture, so every
figure wears the same clothes. Needs per-instance colour variation (hue-shift
the clothing/skin regions per person) and more than one model in the mix.

## V5 — passengers float

> "they seem to float above the floor."

The crowd's base height is a measured platform deck, capped at 1.6 m above
terrain. If a station model's deck is found where there is no deck under a
given figure (or the model was placed at a different height), the figure hangs.
Needs a per-figure grounding check: foot height vs terrain/platform at that
exact x/z.

## V6 — passengers do not board

> "they don't go into the train and out of the train. they should be walking in
> and out."

Today boarding is a number: the crowd count drops and the mesh is rebuilt. The
figures never walk. Needs a boarding animation — people move along the platform
to a door and disappear into the car (and out of it on alighting).

## V7 — real textures for signs, and for trains

> "i want actual proper textures, and if the trains have no textures — they
> should also have them."

The train material is vertex-colour only. This is a real renderer feature: a
textured material for train/station/sign meshes, with the GLB's own images
uploaded as textures and UVs carried through the mesh path (they are currently
discarded). Sign faces then become proper artwork instead of seven-segment
quads.

## V8 — shimmer/aliasing on buildings while moving

> "textures and buildings that would also move a bit or shimmer or something
> like that (looked like aliasing artifacts)."

Possibly the same TAA/motion-vector path fixed for the train in v1.1.5, but for
tiles under camera motion; possibly mipmap/anisotropy settings on the building
atlas; possibly a consequence of V1/V2 re-uploads. Needs the temporal-stability
tool pointed at building regions rather than the train.

## V9 — I could not see any of this

> "the tests also didn't catch the texture issues, nor did you — so you need

Correct, and it is the issue that matters most: every fix above is guesswork

## V1/V2 — ROOT CAUSE FOUND AND FIXED (2026-08-13)

The chain, each link measured rather than assumed:

1. `TileSystem.updateTiles()` **rebuilds the load queue from the CURRENT frustum
   every frame**. Turning the camera therefore queues the tiles you are turning
   toward.
2. `getNextTileToLoad()` refuses to load while `tiles.size >= MaxConcurrentTiles`
   (150 — the cap that exists because a long session once grew to tens of GB).
3. `removeCulledTiles()` frees room by evicting **out-of-frustum** tiles. The
   moment a tile leaves the view it is a candidate — including the street
   directly behind you.
4. A building that spans tiles is drawn by ONE holder tile
   (`TileBuilding.addParent/removeParent` → `hideBuilding`/`showBuilding`).
   Evicting and reloading tiles reassigns holders constantly, so buildings
   disappear, reappear, and are redrawn by a different tile with a different
   `textureId` buffer — **which is exactly "it changes texture every time"**.

Measured on a stationary camera doing one slow turn (train parked):

| | Before | After |
|---|---|---|
| Tile create/destroy | **113 / second** (278 created, 289 destroyed in 5 s) | **1.5 / second** (yaw), **0** (yaw+zoom) |
| Building display patches | 2.1 / frame | **0.01 / frame** |
| Heap growth | +1,980 MB / min | −207 MB / min (GC reclaiming) |
| FPS | 68 | 74 |

**The fix** is two rules in `removeCulledTiles`, plus a batching fix:

- **Retention radius** (`Config.TileRetentionDistance`, 2.5 km): a near tile is
  never evicted for being out of frustum. What is near does not change when the
  camera turns; frustum membership does.
- **Eviction grace period** (`Config.TileEvictionGraceSeconds`, 25 s): a tile
  seen recently is not evicted. Turning the camera is not a reason to throw a
  tile away and fetch it back seconds later.
- `TileExtrudedMesh` now applies all display-buffer patches and uploads **once**,
  instead of uploading the whole buffer once per patch.

Driving still loads tiles normally (6.8 events/s, heap +44 MB/min), so the grace
period does not starve genuinely new geography.
