## V1 — building textures are wrong

> "something weird seems to have happened to textures around the station and in
> the world in general … something that happened in one of the versions lately
> has made the textures not actually apply correctly to the buildings."

Recent candidates, newest first: lineside sign meshes (v1.1.14), rigged
character loading (v1.1.10) which decodes GLB images to a 2D canvas, crowd
meshes rebuilt 5×/s (v1.1.9/v1.1.10), station geometry re-origin (v1.1.9),
motion-vector + TAA changes (v1.1.5).

**Hypothesis (ranked):**
1. Texture-atlas or tile eviction under memory pressure — see V3. If GPU memory
   climbs, the tile system drops and re-uploads building textures, which would
   look exactly like "changes texture every time" (V2).
2. `CharacterLoader` calls `createImageBitmap` + a 2D canvas at load. If that
   disturbs the WebGL context's active texture unit or pixel-store state, the
   next uploads land wrong.

## V2 — buildings pop in/out and re-texture on camera movement

> "moving the camera around at the station seems to be causing the buildings to
> come in and out of view, and they seem to change textures every time."
> "sometimes the correct texture is loaded and applied and then it switches to
> the strange texture that seems diagonally applied"

### MEASURED, 2026-08-13 — the operator's reading was right

Orbiting the camera at a station with the train STOPPED, for ten seconds:

| Signal | Value | Reading |
|---|---|---|
| Buffer creation, blamed | `createAttributeBuffer ← <tile mesh>.updateMesh` ×4 distinct classes | **tile meshes are being rebuilt by camera movement alone** |
| New VAOs | `bindVAO ← draw` for those same classes | each rebuild also makes a new VAO |
| Live buffers | **+1,000 / min** | churn is not being reclaimed fast enough |
| Live VAOs | **+619 / min** | same |
| Heap | **+1,975 MB / min** | this is the "load climbs" symptom, and it needs no driving at all |
| Texture uploads | 54–58 / sec, ALL from `updateWaterTileMask` / `updateTerrainTileMask` | terrain masks, not building textures |

Two conclusions that change the diagnosis:

1. **Building textures are NOT being re-uploaded.** Every texture upload during
   camera movement is a terrain/water mask. So "the texture changes" is not the
   image being replaced — it is the building MESH being rebuilt, and coming
   back with different per-vertex texture ids or a different LOD. The tile
   system is discarding and recreating work purely because the camera moved,
   exactly as the operator suspected.
2. **`UNPACK_FLIP_Y_WEBGL` is toggled 292–384 times** during a single orbit.
   Flip-Y is global WebGL state. A texture uploaded with the flag in the wrong
   position is applied upside down, and combined with a mismatched UV set that
   is precisely the "strange, diagonally applied" look. This is a strong second
   suspect and it is cheap to test: pin the flag and see whether the artifact
   survives.

### Next steps, in order

1. Count tile create/destroy events per second during a camera orbit (needs a
   handle on the tile system in `lib-drive.mjs`; `v.tiles instanceof Map` did
   not match the real field). If tiles are being evicted on camera movement,
   the eviction policy is the bug — a camera orbit does not change which tiles
   are near the train.
2. Pin `UNPACK_FLIP_Y_WEBGL` around every upload and re-run the visual-stability
   probe on the building regions; compare `flipPct` before and after.
3. Only then look at the mesh-rebuild path itself.

**Do not "fix" this by guessing.** The first hypothesis in this file (memory
pressure evicting building textures) is now DISPROVED by measurement — no
building texture was re-uploaded at all.

## V3 — load climbs over time

**This must be measured, not argued.** The tool is a live count of WebGL
objects (buffers, textures, VAOs) sampled over minutes of driving.

## V1/V2 — ROOT CAUSE FOUND AND FIXED (2026-08-13)

The chain, each link measured rather than assumed:

1. `TileSystem.updateTiles()` **rebuilds the load queue from the CURRENT frustum
   every frame**. Turning the camera therefore queues the tiles you are turning
   toward.
2. `getNextTileToLoad()` refuses to load while `tiles.size >= MaxConcurrentTiles`
   (150 — the cap that exists because a long session once grew to tens of GB).
3. `removeCulledTiles()` frees room by evicting **out-of-frustum** tiles. The
   moment a tile leaves the view it is a candidate — including the street
   directly behind you.
4. A building that spans tiles is drawn by ONE holder tile
   (`TileBuilding.addParent/removeParent` → `hideBuilding`/`showBuilding`).
   Evicting and reloading tiles reassigns holders constantly, so buildings
   disappear, reappear, and are redrawn by a different tile with a different
   `textureId` buffer — **which is exactly "it changes texture every time"**.

Measured on a stationary camera doing one slow turn (train parked):

| | Before | After |
|---|---|---|
| Tile create/destroy | **113 / second** (278 created, 289 destroyed in 5 s) | **1.5 / second** (yaw), **0** (yaw+zoom) |
| Building display patches | 2.1 / frame | **0.01 / frame** |
| Heap growth | +1,980 MB / min | −207 MB / min (GC reclaiming) |
| FPS | 68 | 74 |

**The fix** is two rules in `removeCulledTiles`, plus a batching fix:

- **Retention radius** (`Config.TileRetentionDistance`, 2.5 km): a near tile is
  never evicted for being out of frustum. What is near does not change when the
  camera turns; frustum membership does.
- **Eviction grace period** (`Config.TileEvictionGraceSeconds`, 25 s): a tile
  seen recently is not evicted. Turning the camera is not a reason to throw a
  tile away and fetch it back seconds later.
- `TileExtrudedMesh` now applies all display-buffer patches and uploads **once**,
  instead of uploading the whole buffer once per patch.

Driving still loads tiles normally (6.8 events/s, heap +44 MB/min), so the grace
period does not starve genuinely new geography.

## V2 — the wide-view half, found and fixed 2026-08-13 (second pass)

The close-orbit fix (retention radius + grace period) did not hold on a WIDE
view. Measured at pitch 0.85 / distance 420: **35.1 tile events per second**,
117 tiles loaded and 129 destroyed during one slow turn. Two distinct causes,
both found only after the instrument was made to name the removal path
(`tileChurn().removalsByReason`) — every single removal was
`evicted-out-of-frustum`.

**Cause 1 — visible tiles were marked unseen.** The frustum list is capped at
`MaxConcurrentTiles` because a long frustum wants more tiles than the cache can
hold. But `inFrustum` / `lastInFrustumAt` were refreshed from that CAPPED slice,
so a tile ranked 151st was on screen and simultaneously recorded as not looked
at. It then aged past the 25 s eviction grace and was deleted **while visible**.
Fixed by marking visibility from the full frustum list and capping only the
load-request set.

**Cause 2 — the working set rotated.** "Nearest 150 in frustum" is a different
150 tiles at every heading, so a full cache perpetually swapped one set for
another as the camera turned. The request set is now a **disc** around the
camera (`Config.TileWorkingSetDistance`, 3.2 km), which does not rotate; the
frustum only decides load ORDER, so what you are looking at still loads first.

| Wide orbit, one full 360° turn | Before | After |
|---|---|---|
| Tile events | **35.1 / s** (117 created, 129 removed) | **4.3 / s** (15 / 15) |
| `TileExtrudedMesh` rebuilds | 0.65 / frame | **0.12 / frame** |
| `UNPACK_FLIP_Y_WEBGL` toggles | 180 | **32** |
| Heap growth | +1,390 MB / min | **+98 MB / min** |
| FPS | 68 → 70 | 68 → 76 |

Screenshots before and after the turn are now pixel-equivalent: the buildings
stay where they were instead of vanishing and returning.

## Tooling defect found the same day — measurements were of stale code

`tileChurn()` kept returning the OLD shape after a rebuild. The cause was not the
game: the browser was serving a **cached index.html** pointing at a bundle two
builds old (`index.5ca6599f…` while the server served `index.7abc4a2e…`). Every
measurement taken through that page described code that no longer existed.

`openGame()` now appends a cache-buster to the document URL and **asserts** that
the bundle the page loaded is the bundle the server currently serves, throwing
if they differ. An observation tool that can silently measure the wrong build is
worse than no tool, because it produces confident wrong conclusions — which is
exactly what it did.

### The same defect again, one layer down (found while fixing the draw-call cost)

The assertion above compares the **browser** against the **server**. It cannot
catch the case that actually recurred: port 3111 is `node server/dist/index.js`,
a static server for a **built** bundle, not a dev server. Editing a source file
changes nothing until `npm run build` runs, and browser and server then agree
perfectly on a bundle that is two edits old — the assertion passes and the
measurement is fiction.

This produced a confident false result: a run that appeared to show draw calls
falling 262 → 197 was measuring the unmodified build from a different camera
position after driving. The real change, measured after building, was 262 → 164
on the same camera.

`openGame()` now also refuses to run when anything under `src/` is newer than
the served bundle, naming the file and the gap. Verified by touching a source
file and confirming the probe throws instead of measuring.

**Rule for probes: never hand-roll the boot sequence.** Both stale-measurement
incidents happened in inline one-off probes that skipped `openGame()` and its
guards. Use the shared helper; if it lacks something, add it there.

## GPU memory leak: every vertex buffer ever created stayed allocated (FIXED)

This is the likely root of "GPU load seems to go higher the longer I play".

`WebGL2Attribute.delete()` was an **empty method**. `WebGL2Mesh.delete()` called
it faithfully for every attribute, so meshes freed their VAO and index buffer
and silently leaked every vertex buffer they owned. Parked at a station, that
was **357 orphaned buffers every 25 seconds**, for as long as the game ran.

### The instrument had to be fixed first, and it had two faults

`blameKind('createBuffer')` returned `[]`, which was read as "the growth is
unattributable". It was not — the kind is named `buffer`, and an unknown kind
returned an empty array **indistinguishable from "this never happened"**.
`blameKind` now throws and names every kind it does record, and `kinds()` lists
them with their sample rates.

Underneath that, attribution used ONE global counter sampling 1-in-20 of the
whole call stream. `bufferSubData` fires ~11,500/s and `createBuffer` about ten,
so creations were ~0.1% of events and nearly every sampling slot went to a
uniform upload — the rare event, which is precisely what a leak is, was the one
guaranteed to be invisible. Sampling is now per kind, and resource creations are
captured every time.

With that fixed the answer was immediate and arithmetically exact: 476 buffers
created per 25 s (357 attribute + 119 index, from `updateMesh`), against live
growth of 355 per 25 s. 476 − 355 = 121 ≈ the 119 index buffers. Index buffers
were being freed; vertex buffers were not.

### The fix

A buffer cannot simply be freed by the attribute holding it — the tile
mega-buffers deliberately share one buffer across many meshes. `WebGL2AttributeBuffer`
is now reference-counted: attributes `retain()` on construction and `release()`
on delete, freeing only when the last reference goes. Direct `delete()` calls
keep their hard-free semantics and are now double-free safe.

| Idle, 25 s, bundle asserted | Before | After |
|---|---|---|
| Live buffer growth | **+852/min** | **0/min** |
| Live buffers | 2,374 | **1,780** |
| Heap | +6.7 MB/min | −51.6 MB/min |

Validated driving as well as idle (86 tiles streamed, shared mega-buffers
intact, no console errors) with screenshots: trains, tracks, platform,
buildings and passengers all render.

### Left open by this: the churn behind the leak

484 buffers are still CREATED and freed every 25 s while parked — ~4.8
`TrainMeshObject` rebuilds a second with the train stationary. That is no longer
a leak, but it is wasted work with an obvious smell, and it is the next thing to
look at.

## Platform crowds rebuilt their whole mesh 5× a second (FIXED)

The churn left behind by the leak fix. Animated platform crowds re-bake their
figures every `REBUILD_INTERVAL` (0.2 s) so the people visibly move, and the
re-bake path did `removeCrowd()` + `buildCrowd()` — disposing the mesh and
allocating a fresh set of GPU buffers each time. Measured parked at a station:
**476 buffer creations per 25 s, 119 mesh rebuilds**, with nothing moving but
the passengers.

An animation re-bake changes only where the vertices ARE — same platform, same
people, same variants, same detail level — which is exactly what
`TrainMeshObject.updatePositionAndNormalBuffers` exists for. It was unused here.
The re-bake now rewrites the existing buffers in place.

It cannot assume the topology is unchanged: a GLB character finishing its
download mid-run swaps a placeholder figure for a rigged one with a different
vertex count **without changing the variant key**. Buffer lengths are compared
rather than assumed, and a mismatch falls through to a full rebuild.

| Parked at a station, 25 s | Before | After |
|---|---|---|
| Buffer creations | 476 | **8** |
| Mesh rebuilds | 119 | **2** |
| Live buffer growth | 0/min | 0/min |
| FPS | 74 | **77** |

Validated that the passengers still animate rather than freezing: five vertex-
buffer fingerprints sampled 0.7 s apart are all distinct while the buffer length
stays constant at 433,158 floats. (The station screenshot has the camera inside
the platform deck — a `goToStation` framing artefact — so the crowd render
evidence is the earlier driving capture, not that one.)

## V1b — flat pale yellow ground: traced to the biome lookup, NOT yet fixed

Diagnosis only. Recording the trace so the next session does not repeat it.

The terrain colour is built in `src/resources/shaders/terrain.frag`:

```
detailColor = textureNoTile(tDetailNoise, tDetailMaps, 0., ...) * vBiomeColor;
outColor = vec4(detailColor, 1);
...
outColor.rgb = heightblend(outColor.rgb, 1. - usageFactor, usedTerrainColor, usedTerrainHeight);
```

and `vBiomeColor` in `terrain.vert` is:

```
vBiomeColor = texture(tBiomeMap, biomeCoordinates).rgb * 1.5;
```

`biomeCoordinates` is set once per frame in `GBufferPass.renderTerrain` as
`MathUtils.meters2tile(camera.position.x, camera.position.z, 0)` — **zoom 0**, so
the whole planet is a single tile and the value is a UV into a world biome map.
For Tel Aviv that lands in the arid band, and the `* 1.5` boost brightens it
toward the pale yellow that covers the screen.

So the base colour being sand is arguably correct for the climate. The variety
that should break it up comes from the SECOND term: `usedTerrainColor` from
`tUsageMaps`, height-blended by `usageFactor`, which is derived from
`tUsageMask` / `tUsage` (the landuse rasterisation, produced by
`TerrainTexturesPass`). If `usageFactor` is always 0, every non-road,
non-water, non-building surface renders as pure boosted biome colour — exactly
the observed symptom.

**Next step, and it is a measurement, not a change:** confirm whether the usage
mask is populated. In `terrain.frag` the mask is read as
`texelFetch(tUsageMask, ...).r` and a `layerIndex` of 255 means "no landuse for
this tile". If that branch is always taken, the fault is upstream in landuse
rasterisation, not in the shader — and the `* 1.5` boost is a red herring worth
resisting, since dimming it would only make a uniform surface a darker uniform
surface.

## The measurement was wrong, and fixing it changed the conclusions

The operator pushed back on the frame-rate figures quoted for the render work,
and was right. Three faults, each found by validating the instrument instead of
trusting it.

**1. Frame rate is not a throughput metric here.** `requestAnimationFrame` is
vsync-locked, so fps cannot exceed the display refresh; a frame limiter pins it
lower still. "74 → 77 fps" was two numbers sitting at a cap. The in-game HUD read
120 at the same moment, which should have given it away. **Retracted.**

**2. The first GPU timer measured the vsync period.** It opened a query at one
animation frame and closed it at the next, bracketing the render *and* the idle
gap. Caught by varying the pixel count: the number sat flat at ~13 ms. It now
opens on a frame's first draw and closes in a microtask once the render has
unwound. Validated: render scale 1.0 → 0.5 moves it 10.26 → 5.29 ms, shadows off
moves it 10.06 → 8.88 ms, repeats agree to ~1%.

**3. Frames were counted as animation-frame callbacks.** A limiter skips the
render on some ticks, so on a 120 Hz panel capped at 60 the telemetry reported
120 frames/s and every per-frame figure was diluted by two. Now a frame is
counted when it draws.

### What the corrected A/B actually says

Idle, identical pinned settings, locked 60 fps, both builds measured with the
same instrument:

| | BEFORE (786e4c3) | AFTER |
|---|---|---|
| **GPU utilisation** | **53.9%** | **52.6%** |
| GPU median | 8.981 ms | 8.769 ms |
| Draw calls | 262/frame | 141/frame |
| `bufferSubData` | 17,272/s | 9,110/s |
| Buffer growth | +806.7/min | **0/min** |

**Cutting draw calls 46% moved GPU utilisation by 1.3 points — noise.** The
frame is FILL-RATE bound: halving the render scale halves GPU time, while
halving draw calls changes nothing. The culling and upload work reduced CPU-side
submission and memory, not GPU cost. The unambiguous win is the leak.

A correction of my own: I reported `renderScale` as inert. It is not — it is a
`selectRange` setting driven by `numberValue`, and my probe was setting
`statusValue`. Driven correctly it resizes the buffer 1280×800 → 640×400 exactly
as intended.

## Auto-quality governor now steers on GPU cost (FIXED)

Applying the above to the governor, per the operator's request.

It measured frame rate alone, which cannot answer the question it exists to ask:
how much headroom is there. Under a cap the rate sits at the target whether the
GPU is 30% or 99% busy, so the up-step climbed blind until the rate finally
broke, and it could not see a machine holding 60 only just.

`GpuFrameTimer` (`src/app/systems/GpuFrameTimer.ts`) now runs always-on in
`RenderSystem` around `renderGraph.render()`, and the governor uses GPU cost as
a fraction of the frame budget: step down on sustained load above 90% even while
the rate is met, and require measured headroom below 65% before stepping up or
uncapping. With no timer extension it falls back to the old rate-only behaviour.

### Two real bugs this exposed, both fixed

**The step-effectiveness audit asked the frame rate.** Under a cap the answer is
30 before and 30 after, so EVERY down-step was judged useless, reverted, and
down-stepping locked for three minutes — **a capped game could never shed load,
however hard the GPU was working.** The audit now asks GPU cost.

**An ineffective step was always treated as "quality is not the bottleneck".**
Rungs 0 and 1 both render at full scale, so on a fill-bound frame stepping 0→1
genuinely changes nothing — the audit correctly said so, reverted, and stranded
the player. That response is only right when the GPU has headroom. Over budget,
an ineffective step means it was not big enough, so the governor now keeps
descending to reach the render-scale rungs.

Validated live at 4× pixels (2560×1600), auto engaged, cap at 30:

| | rung | renderScale | GPU ms |
|---|---|---|---|
| settled | 0 | 1.0 | 11.5 |
| overloaded | 0 | 1.0 | 68.9 |
| after fix | 1 → 2 → 3 → 4 → **5** | **0.75** | **14.7** ✓ |

Before the fix it sat at rung 0 and 71.8 ms indefinitely, `gpuTightCount`
climbing to 45 with no action. It now descends to the lever that matters, gets
back inside budget, and stops rather than spiralling to the floor.
