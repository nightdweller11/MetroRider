### 3. Memory (the 30 GB browser incident)
Root causes found by code audit, all fixed:
- **Tile eviction was effectively unbounded** — only out-of-frustum tiles beyond
  the cap were evicted, so a wide/high view kept every visible tile forever.
  Now: hard cap gates loading (`TileSystem.getNextTileToLoad`), eviction is
  demand-driven (frees room for queued tiles), plus a farthest-visible safety net.
- **Mega-buffer allocators never compacted** — frees punched holes, `used` only
  grew, every overflow DOUBLED the buffer (CPU mirror + GPU) permanently.
  Now: `MegaBufferAllocator.maintain()` (compact + shrink) runs from the render
  loop every 240 frames, one allocator per tick.
- **Projected + hugging geometry was mega-buffered but never drawn from there**
  (only extruded has a batch path) — two dead copies of most tile geometry.
  Removed those groups.
- **`TileObjectsSystem.buildingsList` never deleted entries** → entry per
  building ever seen. Fixed.
- **~250 startup images (92 MB PNGs) pinned forever** — released after GPU
  upload (`ResourceLoader.releaseImages()`, frame 300).
- **Default FPS cap 60** (was uncapped: 133 fps, GPU process at ~100% CPU).
- Tests: `megaBufferMaintenance.test.ts` (3) + updated integration tests.
- Measured (production build, 140 s full-throttle driving on the Israel-railways
  map with a 5-GLB consist): tiles flat at 150; allocator capacity oscillates
  9–23 MB (shrink works); renderer RSS sawtooths 750 MB–1.1 GB and RETURNS to
  ~740 MB; GPU process 240–360 MB. No ratchet.

## Seventh round (2026-08-12): v1.1.4 "The Gearbox Update" — auto-quality rebuilt on user feedback
- User-reported failure reproduced in tests: governor descended rung 1→7 on a
  fast machine. TWO real causes found by instrumentation (getDebugSnapshot):
  (1) the v1.1.3 carried-timestamp FPS limiter ran AHEAD of real time after any
  missed vsync tick, locking a 16.7/25 ms beat (≈48 fps) on 120 Hz displays —
  the governor was correctly reporting a real deficit the limiter created;
  (2) frame jitter from streaming/CPU is quality-INDEPENDENT, so down-steps
  never helped and the governor chased the metric to the floor.
- Fixes: accumulator FPS limiter (banks real elapsed time; "30"→29.9 measured,
  no run-ahead); per-second average-fps buckets + median across 8 s; generous
  0.85×target down threshold (a capped average can never exceed the cap);
  **step-effectiveness audit** — a down-step that doesn't improve the median
  ≥5% is REVERTED and down-stepping locks 180 s; when degrading is locked or
  floored and 60 still fails, the governor retargets a steady 30 instead of
  ruining visuals.
- One Graphics tier knob replaces performanceMode+autoQuality:
  low/medium/high/auto/custom. Tier picks apply their preset immediately
  (persisted); High-end = max settings + uncapped. Auto acts ONLY when
  selected; manually changing a governed setting flips the tier to Custom.
- Verified: presets apply; manual-in-tier untouched; auto override→custom;
  fast machine explores, reverts ineffective steps, stabilizes (no spiral);
  8× throttle degrades where effective and retargets 30.
